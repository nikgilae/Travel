# Перенос статики фронта с Vercel на сервер 72.56.34.52

Причина: нестабильный сетевой путь из российских сетей до anycast-IP
Vercel — подтверждено замерами (см. обсуждение в issue/чате), до 40%
`Connect timeout` на загрузке JS-бандла с реальной ноды в Москве,
против 0% сбоев на нашем сервере.

## Порядок выполнения

Каждый скрипт помечен, где его выполнять — **на ноутбуке** или
**на сервере** (в уже открытой SSH-сессии).

| # | Скрипт | Где | Статус |
|---|--------|-----|--------|
| 0 | `00-recon.sh` + `00b-recon-remainder.sh` | сервер | ✅ выполнено |
| 1 | `10-setup-dirs.sh` | сервер | далее |
| 2 | скопировать `nginx-tourrhythm.ru.conf` | ноутбук → сервер (scp) | далее |
| 3 | `20-enable-site.sh` | сервер | далее |
| 4 | `deploy.sh` (первый релиз) | ноутбук | далее |
| 5 | `25-check-dns.sh` | ноутбук или сервер | ⏳ ждём — DNS ещё не везде разошёлся |
| 6 | `30-certbot.sh` | сервер | **только после** зелёного света в шаге 5 |
| 7 | Проверка через check-host.net с RU-ноды | делаю я | после шага 6 |
| 8 | Наблюдение / решение по Vercel-проекту | вместе | после шага 7 |

### Шаг 1 — на сервере
```bash
scp frontend/deploy/10-setup-dirs.sh root@72.56.34.52:/tmp/
ssh root@72.56.34.52 "chmod +x /tmp/10-setup-dirs.sh && /tmp/10-setup-dirs.sh"
```

### Шаг 2 — с ноутбука, копируем конфиг
```bash
scp frontend/deploy/nginx-tourrhythm.ru.conf root@72.56.34.52:/etc/nginx/sites-available/tourrhythm.ru
```

### Шаг 3 — на сервере, включаем сайт
```bash
scp frontend/deploy/20-enable-site.sh root@72.56.34.52:/tmp/
ssh root@72.56.34.52 "chmod +x /tmp/20-enable-site.sh && /tmp/20-enable-site.sh"
```
На этом этапе сайт слушает порт 80 на сервере, но реального трафика
туда ещё почти нет — большинство резолверов ещё смотрят на Vercel.
Это безопасно: мы просто готовим цель к моменту переключения.

### Шаг 4 — с ноутбука, первый деплой
```bash
bash frontend/deploy/deploy.sh
```
После этого `http://72.56.34.52/` (по IP, с заголовком Host: tourrhythm.ru)
уже должен отдавать актуальную сборку. Можно проверить так:
```bash
curl -H "Host: tourrhythm.ru" http://72.56.34.52/
```

### Шаг 5 — ждём DNS, проверяем периодически
```bash
bash frontend/deploy/25-check-dns.sh
```
Гоняй эту команду раз в 15-20 минут. Как только увидишь ✅ для ОБОИХ
доменов у ОБОИХ резолверов — переходи к шагу 6. Присылай мне вывод,
я подтвержу, что можно запускать certbot.

### Шаг 6 — на сервере, только после зелёного света
```bash
scp frontend/deploy/30-certbot.sh root@72.56.34.52:/tmp/
ssh root@72.56.34.52 "chmod +x /tmp/30-certbot.sh && /tmp/30-certbot.sh"
```

### Шаг 7 — проверка с реальной RU-точки
Это делаю я сам (через check-host.net, независимую от твоего сервера
и от VPN) — прогоняю ту же серию запросов, что и в начале обсуждения,
и сравниваю % успехов до/после.

### Шаг 8 — судьба Vercel-проекта
Не удаляем и не отключаем сразу. Держим как холодный резерв минимум
несколько дней — если что-то всплывёт (нестандартный edge-case роутинга,
CDN-специфичное поведение), откат — это просто вернуть старую A-запись
обратно, без пересборки и без потери кода (сам Vercel-деплой никуда
не делся).

## Откат в любой момент

Откат DNS: вернуть A-запись `tourrhythm.ru`/`www` на `216.198.79.1`
в панели регистратора — то же место, где меняли на новый IP.

Откат релиза (если сама сборка на сервере багованная, а не проблема
инфраструктуры):
```bash
ssh root@72.56.34.52 "ls -1t /var/www/tourrhythm.ru/releases"
ssh root@72.56.34.52 "ln -sfn /var/www/tourrhythm.ru/releases/<предыдущий> /var/www/tourrhythm.ru/current"
```
Мгновенно, без пересборки.
