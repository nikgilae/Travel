# Фронтенд — план изменений под RAG/бэкенд-доработки

> Точка входа для фронтенд-работы, вытекающей из `RAG-POI-PLAN.md` и
> `PRODUCT-FEATURES.md`. Написано 2026-08-18 после чтения реального кода
> фронта (`frontend/src`), не по памяти о том, что там «должно быть». Формат —
> по образцу `RAG-POI-PLAN.md`: факты → итерации → тесты. Без уведомлений
> (сняты с рассмотрения решением от того же дня).

## Установленные факты (проверено в коде, не предполагалось)

Это меняет объём работы по каждому пункту — без этого раздела план выглядел
бы куда объёмнее, чем есть на самом деле.

1. **RAG (векторный отбор POI) не требует изменений на фронте вообще.**
   Контракт `POST /trips/{id}/generate` не меняется — ответ имеет ту же форму
   (`days[].main_pois[]/additional_pois[]`), просто места внутри подобраны
   лучше. Фронт получает более релевантный список тем же кодом, что и
   сейчас. Единственная фронтовая работа по RAG — если решите поменять UX
   генерации (например, добавить лоадер с объяснением, что идёт подбор) — но
   это не обязательно и не в этом плане.

2. **`planned_start_time` уже читается фронтом.** В `TripPlanScreen.jsx`
   есть `formatTime(p.planned_start_time)` ([TripPlanScreen.jsx:549](frontend/src/pages/TripPlanScreen.jsx#L549),
   [:1446](frontend/src/pages/TripPlanScreen.jsx#L1446)) — фронт готов к
   этому полю уже сейчас. Проблема была только на бэкенде (поле всегда
   `None`, см. `RAG-POI-PLAN.md`). Как только бэкенд начнёт присылать реальное
   значение — оно просто начнёт отображаться, без единой правки фронта.
   Важно только свериться с форматом: `formatTime` делает
   `new Date(dt).toTimeString()` — бэкенду нужно отдавать ISO 8601 с
   таймзоной (`TIMESTAMPTZ` в модели это и так гарантирует через FastAPI
   сериализацию Pydantic).

3. **Бюджет уже considers по-своему — и небанально.** В `TripPlanScreen.jsx`
   есть таб «БЮДЖЕТ» ([TripPlanScreen.jsx:44](frontend/src/pages/TripPlanScreen.jsx#L44))
   и целый самодельный парсер денежных строк — `CURRENCY_TOKENS`,
   `parseEstimate`, `detectCurrency` ([TripPlanScreen.jsx:47-93](frontend/src/pages/TripPlanScreen.jsx#L47)).
   Комментарий в коде — осознанное решение: *«budget_estimate приходит от AI
   уже в валюте страны назначения... Мы складываем реальные суммы по местам
   дня и показываем в этой валюте — без перевода в рубли»*. То есть
   регекс-парсинг свободной строки от AI — это не недосмотр, а сознательный
   компромисс на момент написания. Как только на бэкенде появится
   структурированная оценка бюджета (число + код валюты, не строка для
   парсинга регэкспом) — этот парсер целиком устаревает и должен быть
   удалён, а не дополнен. Это упрощение кода, а не просто новая фича.

4. **Часы работы и рейтинг уже отрисовываются — но для другого источника
   данных.** В `NearbyPage.jsx` есть готовый UI-паттерн: `StarRating`,
   индикатор `place.opening_hours?.open_now` ([NearbyPage.jsx:97-152](frontend/src/pages/NearbyPage.jsx#L97)).
   Но это работает с `/places/nearby` — эндпоинтом, который **напрямую**
   проксирует живой Google Places Nearby Search ([places.py:63-77](backend/app/api/places.py#L63)),
   а не с сохранёнными в БД `POI`, которые видит `TripPlanScreen`. У модели
   `POI` в БД поля `opening_hours` вообще нет. Значит: (а) визуальный паттерн
   для часов работы/рейтинга уже придуман и его можно переиспользовать, но
   (б) для `TripPlanScreen` его придётся подключать заново, к другому
   источнику данных — это не копипаст одного компонента, а два разных
   бэкенд-контракта, которые надо не перепутать.

5. **`ActiveTripPage.jsx` — полностью статичный макет, не подключён к
   данным.** Список мест дня захардкожен (`const POIS = [...]`, «Пантеон»,
   «Фонтан Треви» — Рим, не реальный трип пользователя), кнопка «Найти
   рядом» — заглушка с текстом «подключится с API карт»
   ([ActiveTripPage.jsx:8-14](frontend/src/pages/ActiveTripPage.jsx#L8),
   [:196-198](frontend/src/pages/ActiveTripPage.jsx#L196)). Это дизайн-прототип
   экрана «я в поездке прямо сейчас», не рабочая страница. Любая функция,
   которая должна проявляться именно во время поездки (предупреждение о
   закрытии, погода на сегодня, живая логистика) — физически негде
   показывать, пока эта страница не подключена к реальным данным трипа. Это
   не мелкая доработка «до кучи» — это блокирующая предпосылка для целого
   класса функций из `PRODUCT-FEATURES.md`.

6. **Чат рендерит только плоский текст.** `ChatScreen.jsx` работает с
   сообщениями вида `{ sender, text }` ([ChatScreen.jsx:98-99](frontend/src/components/ChatScreen.jsx#L98),
   [:220-258](frontend/src/components/ChatScreen.jsx#L220)) — нет понятия
   структурированного контента (карточка отеля с кнопкой, бейдж
   предупреждения, что-то, что не является строкой текста). Тулы, которые
   возвращают структурированные данные (поиск отелей/рейсов, предупреждение
   о логистике) сейчас физически некуда положить в чате, кроме как
   отформатировать в текст самим текстом ответа модели — что работает, но
   не даёт настоящих интерактивных элементов (кнопка «Забронировать →»
   как реальная кнопка, а не текстовая ссылка).

7. **Стилевой язык уже устоявшийся и его нельзя ломать новыми элементами.**
   Палитра `TR` в `TripPlanScreen.jsx` (`bg #F6F7F9`, `surface #FFFFFF`,
   `fg #0A0B0C`, `lime #B9FF3D`, `warn #B43340`), моноширинный JetBrains Mono
   для лейблов/таймкодов, hairline-бордеры вместо теней, круглые статусы
   (✓/→/○) в `ActiveTripPage`. Новые элементы (бейдж цены, предупреждение о
   закрытии, погода) должны говорить на этом же языке, а не приносить свою
   визуальную систему — иначе они будут читаться как чужеродные вставки.

## Принципы для новых UI-элементов

- **Один акцент — один смысл.** `lime (#B9FF3D)` в текущем UI означает
  «выбрано / активно / основное действие» (кнопки, статус «сейчас»,
  подсветка активного таба). Не занимать лайм под предупреждения или
  нейтральную информацию (цена, часы работы) — для этого уже есть `warn
  (#B43340)` и нейтральный `fgMute (#5B6066)`. Смешение приведёт к тому, что
  лайм перестанет считываться как «действие».
- **Лейблы и мета-данные — JetBrains Mono, uppercase, letter-spacing** (уже
  паттерн в `ДНИ`/`КАРТА`/`БЮДЖЕТ` табах, «РИТМ ДНЯ» в `ActiveTripPage`).
  Новые метки («15 мин пешком», «$$», «закрыто по вт») — тот же регистр и
  шрифт, не новый стиль текста.
- **Предупреждения говорят фактами, не извиняются.** «Закрыто по
  вторникам» — не «К сожалению, это место может быть закрыто, уточните
  пожалуйста». Прямой, конкретный, действие-ориентированный тон, тот же,
  что уже в остальном интерфейсе (короткие лейблы, не разговорный тон).
- **Бейдж, не карточка, для одного факта.** Часы работы, уровень цен,
  время в пути — это по одному факту на POI, они должны быть маленькими
  инлайн-бейджами рядом с существующими `💰`/`💡` пометками в карточке места
  ([TripPlanScreen.jsx:1502-1519](frontend/src/pages/TripPlanScreen.jsx#L1502)),
  не отдельными блоками — иначе карточка места разрастётся и потеряет
  иерархию.
- **Внешние ссылки (отели/рейсы) — это единственное место, где нужен новый
  паттерн компонента**, потому что ничего похожего в дизайне ещё нет: карточка
  с явным обозначением «уходите из приложения» (иконка внешней ссылки,
  не просто текст) — честно, не маскировать под внутреннее действие.

## Итерации

### Итерация 0 — Ничего не делать для RAG

Явно фиксирую отдельным пунктом: RAG-часть бэкенд-плана не порождает работы
на фронте. Если после Итерации 3 бэкенд-плана понадобится показывать
пользователю, почему предложены именно эти места (объяснимость подбора) —
это отдельное решение, не часть текущего фронтенд-плана, и не должно
блокировать бэкенд-работу.

### Итерация 1 — Проверка `planned_start_time` на реальных данных

**Что делать:** после того как бэкенд начнёт заполнять `planned_start_time`
(Итерация 0 `RAG-POI-PLAN.md`/связанная доработка) — прогнать реальный трип
и свериться, что `formatTime` корректно парсит присланный формат. Скорее
всего доработок не потребуется вообще — компонент уже написан правильно под
ISO-строку с таймзоной.

**Приёмка:** время отображается в карточке места без правок кода фронта.
Если формат не совпал — это баг сериализации на бэкенде, не повод менять
фронт под конкретный формат бэкенда.

### Итерация 2 — Структурированный бюджет вместо регэксп-парсера

**Что делать:**
- Согласовать с бэкендом новый формат `budget_estimate`: объект
  `{ amount: number, currency: str }` вместо свободной строки, которую
  сейчас парсит `parseEstimate`. Это прямое следствие backend-фичи «курс
  валют» и «`price_level`» из `PRODUCT-FEATURES.md` — там уже появляются
  реальные числа, разумно отдавать их структурированно, а не сериализовать
  в текст и заставлять фронт парсить обратно.
- Удалить `CURRENCY_TOKENS`, `detectCurrency`, `toNumber`, `parseEstimate`
  ([TripPlanScreen.jsx:47-93](frontend/src/pages/TripPlanScreen.jsx#L47)) —
  не оставлять как fallback «на всякий случай», код без функции гниёт
  тише, чем код с функцией, но продолжает всех путать.
- Таб «БЮДЖЕТ»: добавить статус-бейдж соответствия заявленному уровню
  бюджета поездки (`trip.budget: low/medium/high`) — бэкенд теперь считает
  это на генерации (см. `PRODUCT-FEATURES.md`, раздел 2), фронту остаётся
  только показать результат: `✓ В рамках бюджета` / `⚠ Дороже среднего на
  N%`, тем же `warn`-цветом, что уже есть в палитре.
- **Открытый вопрос, не решать в одиночку:** показывать ли бюджет
  по-прежнему в валюте назначения (текущее сознательное решение) или
  добавить переключение в валюту пользователя теперь, когда конвертация
  есть на бэкенде? Это продуктовое решение, не техническое — вынести
  отдельным вопросом, не менять умолчание молча.

**Приёмка:** таб «БЮДЖЕТ» отображает те же суммы без регэксп-парсинга,
плюс новый статус-бейдж. Old-parser код удалён, не закомментирован.

### Итерация 3 — Часы работы и уровень цен на карточке места в плане

**Что делать:**
- Новый общий компонент (например `PoiFactBadges.jsx` в `components/`) —
  переиспользуемый набор мелких бейджей: часы работы (открыто/закрыто на
  дату посещения из `TripPOI.day_number`/`planned_start_time`, не «сейчас»
  — это план на будущее, не live-статус), уровень цен (`$`–`$$$$`).
  Визуально — по образцу уже существующего `StarRating`/индикатора открытости
  в `NearbyPage.jsx` ([NearbyPage.jsx:97-152](frontend/src/pages/NearbyPage.jsx#L97)),
  но не импорт напрямую — тот завязан на другой, живой источник данных
  (`/places/nearby`), а не на сохранённый `POI` из плана поездки.
- Встроить в карточку места в `TripPlanScreen.jsx` рядом с уже существующими
  `💰`/`💡` пометками ([TripPlanScreen.jsx:1502-1519](frontend/src/pages/TripPlanScreen.jsx#L1502)).
- Если место закрыто на запланированную дату — не просто бейдж, а явное
  предупреждение таким же `warn`-цветом, что уже используется в палитре, с
  прямой формулировкой («Закрыто по средам»), не мягкой.

**Приёмка:** новый компонент используется в `TripPlanScreen`, не дублирует
логику `NearbyPage`. Ревью: цветовая консистентность с уже принятой
палитрой `TR` — не вводить новых цветов вне неё.

### Итерация 4 — Логистика между точками дня

**Что делать:**
- Между соседними карточками мест внутри одного дня — маленький разделитель
  с временем в пути («🚶 15 мин» / «🚕 8 мин»), не отдельный блок. Данные —
  из соответствующего бэкенд-тула (`PRODUCT-FEATURES.md`, раздел 2).
- Если логистика физически нереалистична (бэкенд это уже проверяет на
  генерации) — карточка следующего места получает тот же `warn`-акцент, что
  и «закрыто», с коротким текстом причины.

**Приёмка:** разделитель между карточками показывает время в пути там, где
данные есть; молча ничего не показывает там, где бэкенд их не прислал (не
выдумывать на фронте).

### Итерация 5 — Погода: честное состояние «неизвестно», не пустое место

**Что делать:**
- Если бэкенд прислал прогноз на день (трип близко по датам, укладывается в
  горизонт достоверности — `RAG-POI-PLAN.md`/`PRODUCT-FEATURES.md`, раздел
  0) — показать компактный погодный чип у заголовка дня (тот же ряд, где
  сейчас день недели/дата в `TripPlanScreen`).
- Если прогноза нет (трип слишком далеко) — **не показывать пустоту молча**
  и не показывать заглушку-плейсхолдер, который выглядит как баг. Явно,
  но ненавязчиво: «Прогноз появится ближе к поездке» — тем же
  `fgMute`-цветом, что и прочие вторичные подписи. Это прямое следствие
  решения не обманывать пользователя мнимой точностью (обсуждали в
  `PRODUCT-FEATURES.md`, раздел 0) — молчание тут так же нечестно, как
  выдуманный прогноз.

**Приёмка:** оба состояния (есть прогноз / рано для прогноза) отрисованы
явно, не через пустой рендер.

### Итерация 6 — Поиск отелей/рейсов (search & redirect)

**Что делать:**
- Новый, единственный по-настоящему новый визуальный паттерн в этом плане:
  карточка внешнего предложения (отель/рейс) с ценой, кратким фактом и
  явной кнопкой ухода во внешний сервис (иконка внешней ссылки — не маскировать
  под внутреннее действие приложения, см. принципы выше).
- Разместить как отдельную секцию в `TripPlanScreen` (рядом с табами
  «ДНИ»/«КАРТА»/«БЮДЖЕТ» — четвёртый таб, либо блок в существующем виде
  плана) — открытый вопрос по месту, не по визуальному паттерну самой
  карточки.
- Чат: если агент вызывает тул поиска отелей/рейсов, результат должен
  рендериться как эта же карточка внутри диалога, не как форматированный
  текст — это требует Итерации 7 (структурированный контент в чате), не
  делается изолированно раньше неё.

**Приёмка:** карточка визуально отличима от внутренних действий приложения
(понятно до клика, что это уход наружу), использует минимум один новый, но
согласованный с `TR`-палитрой элемент — не десять.

### Итерация 7 — Структурированный контент в чате

**Что делать:**
- Расширить формат сообщения в `ChatScreen.jsx` с `{ sender, text }`
  ([ChatScreen.jsx:220-222](frontend/src/components/ChatScreen.jsx#L220)) до
  `{ sender, text, blocks?: ContentBlock[] }`, где `ContentBlock` — заранее
  ограниченный набор типов (`hotel_card`, `flight_card`, `warning`), не
  произвольный HTML от модели (важно по безопасности — не рендерить
  сырой HTML/markdown, который пришёл от LLM, напрямую).
- Это требует согласованного контракта с бэкендом: `TravelAgentService`
  должен возвращать не только текст, но и структурированные данные тула
  отдельным полем, когда тул это поддерживает — сейчас `process_message`
  возвращает только строку ([chat_agent.py:179](backend/app/services/chat_agent.py#L179)).
  Это одновременно фронт- и бэкенд-работа, не чисто фронтовая итерация —
  делать согласованно, не раньше того, как бэкенд готов отдавать
  структуру.

**Приёмка:** карточка отеля/рейса, вызванная из чата, выглядит так же, как
в Итерации 6 (переиспользование компонента, не два разных визуальных
языка для одного и того же).

### Итерация 8 (блокирующая предпосылка для «во время поездки») — подключить `ActiveTripPage.jsx` к реальным данным

**Что делать:** заменить захардкоженный `POIS` ([ActiveTripPage.jsx:8-14](frontend/src/pages/ActiveTripPage.jsx#L8))
на реальный запрос текущего дня активной поездки пользователя (по аналогии
с тем, как `TripPlanScreen` уже получает план). Определить, что значит
«активный день» — по `trip.start_date` + текущая дата, не по ручному выбору.
Заменить заглушку «Найти рядом» на реальный вызов уже существующего
`/places/nearby` (тот же паттерн, что в `NearbyPage.jsx`) — не изобретать
новый эндпоинт для того, что уже есть.

**Почему это отдельная итерация, а не мелкая правка:** без неё погода «на
сегодня», предупреждение о закрытии «прямо сейчас», живая логистика — всем
им физически некуда попасть на экран. Другие итерации (3-5) работают на
`TripPlanScreen` (план до поездки) независимо от этой; но всё, что должно
проявляться **во время** поездки, ждёт именно этого шага.

**Приёмка:** страница показывает реальный день реальной поездки
пользователя, не демоданные по Риму.

## Тестирование

Проект не описывает отдельно фронтенд-тесты в `CLAUDE.md` (только
`npm run lint`/`npm run build`) — если тестов сейчас нет, не заводить их
специально под этот план отдельной темой; проверка — ручной прогон
`npm run dev` на реальном трипе после каждой итерации, как и остальной
фронт сейчас, судя по составу репозитория.

## Явно не в этом плане

- Push/Telegram-уведомления — сняты с рассмотрения целиком (см.
  `PRODUCT-FEATURES.md`, раздел 5).
- Полноценная транзакция бронирования внутри приложения — не входит,
  только карточка с диплинком наружу (Итерация 6).
- Локальные события/праздники — не включены в этот план: у функции ещё не
  решён источник данных на бэкенде (`PRODUCT-FEATURES.md`, раздел 3),
  фронтовый компонент для неё не проектируется, пока это не решено.
