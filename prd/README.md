# Tourry (внутреннее имя API: «Smart Travel Companion») — Продуктовые требования (PRD)

> Документ сгенерирован реверс-инжинирингом кодовой базы. Дата генерации: 2026-08-05.
> Источник: `/home/nikita/TRAVEL` (backend: FastAPI + PostgreSQL/PostGIS; frontend: React 19 + Vite).

## 1. Обзор системы

**Tourry** (в бренд-текстах чата также встречается «TourRhythm») — сервис планирования путешествий с AI-ассистентом. Пользователь проходит короткий онбординг (страна → город → состав группы → даты → стиль поездки → бюджет → пожелания), после чего система:

1. При необходимости «обогащает» базу точек интереса (POI) города данными Google Places (с cooldown 24 часа на город);
2. Отправляет ИИ (OpenAI-совместимая LLM) список POI города, правила (визовые/культурные/специфичные для места) и предпочтения пользователя;
3. Получает от ИИ по каждому дню поездки набор «основных» и «запасных» точек с расчётным бюджетом, временем посещения и уровнем активности;
4. Позволяет пользователю донастраивать маршрут — заменять, удалять, финализировать порядок точек на день (алгоритм ближайшего соседа по координатам), — как через обычный UI, так и через AI-чат с function calling (агент может сам менять маршрут).

Дополнительно приложение предоставляет: поиск точек «рядом» через прокси Google Places, отображение маршрута на карте, разбивку бюджета по дням, и свободный (не привязанный к поездке) чат с ассистентом для общих вопросов о путешествиях.

**Основной пользователь**: частное лицо, самостоятельно планирующее поездку (leisure/business/education/other), в одиночку или группой. Судя по инфраструктуре (алерты в Telegram как резервный канал «на случай недоступности Sentry из российской инфраструктуры», русскоязычный интерфейс без i18n), целевой рынок — русскоязычные пользователи.

**Технологический стек**:
- Backend: FastAPI, async SQLAlchemy 2.0 + asyncpg, PostgreSQL с расширением PostGIS (геопоиск), JWT-аутентификация (HS256, безрефрешевый токен на 3 часа), Alembic-миграции.
- AI-слой: два независимых сервиса — `generate_trip` (одноразовая генерация маршрута) и `TravelAgentService` (стейтфул-агент с tool calling поверх WebSocket).
- Frontend: React 19 + Vite, react-router-dom v7, Google Maps JS SDK, без state-менеджера (Context API) и без i18n-библиотеки (весь текст — хардкод на русском).
- Мониторинг: Sentry (опционально) + Telegram-алерты для 5xx, structured JSON логи вместо отдельной таблицы событий (осознанное MVP-решение при <20 пользователей).

## 2. Обзор модулей

| Модуль | Экраны / API-группы | Основной функционал |
|---|---|---|
| Аутентификация | Вход, Регистрация | Регистрация/логин по email+паролю, выдача JWT, флаг `is_first_login` для маршрутизации в онбординг |
| Онбординг | 6 экранов-шагов | Сбор параметров будущей поездки: страна/город, состав группы, даты, стиль, бюджет, пожелания → создание поездки + запуск AI-генерации |
| География | (только API, экранов нет) | Справочник стран/городов, контекстная информация о городе для правил |
| Поездки (Trips) | Дашборд, Экран маршрута | CRUD поездок, генерация маршрута ИИ, управление POI в поездке (добавление/удаление/замена/финализация дня) |
| Точки интереса (POI) | Экран маршрута, Рядом | Поиск, обогащение из Google Places, геопоиск «рядом» (PostGIS), детали места |
| Правила (Rules) | Модалки/баннеры в маршруте | Контекстные предупреждения (визовые, культурные, специфичные для точки), привязка к стране/городу/POI с флагом строгости |
| AI-чат | Общий чат, Чат по поездке | Свободный чат без контекста поездки (REST) и стейтфул-агент с function calling по WebSocket, умеющий менять маршрут |
| Места (Google Maps прокси) | Используется внутри «Деталей места» и «Рядом» | Поиск, детали, фото, geo-поиск через Google Places API |
| Мониторинг | — | Приём клиентских ошибок (`/client-errors`), health-check, Sentry/Telegram алерты |

## 4. Глобальные технические заметки

### Модель авторизации
- JWT Bearer-токен (HS256), время жизни **180 минут (3 часа)**, без refresh-механизма — по код-комментарию это «временное решение до появления refresh-токенов».
- Frontend хранит токен в `localStorage` (`access_token`), без проверки истечения и без 401-интерсептора — при истечении токена запросы просто падают с ошибкой в UI.
- `ProtectedRoute` на фронте проверяет только *наличие* токена в localStorage, не его валидность.
- Владение ресурсами (поездками) проверяется через `NotFoundException` (404), а не `ForbiddenException` (403) — чтобы не раскрывать существование чужих объектов. Класс `ForbiddenException` определён в коде, но нигде не используется.

### Состояние POI внутри поездки — ключевая модель данных
Одна и та же таблица `trip_pois` обслуживает два разных состояния одновременно:
1. **Пул после AI-генерации**: POI на конкретный день имеют `poi_status` (`main`/`additional`) и `is_selected=False`, `sequence_order=None` — точки ещё не упорядочены.
2. **Финализированный маршрут дня**: после вызова «Финализировать план дня» точки получают `is_selected=True` и порядковый `sequence_order`, рассчитанный алгоритмом ближайшего соседа (nearest-neighbor, формула Haversine) — а не тем порядком, в котором их предложил ИИ.

Это состояние — центральный UX-паттерн приложения: «сгенерировано → пользователь донастраивает (заменить/удалить через свайп или через AI-чат) → финализировать → маршрут на день готов».

### AI-агент по поездке (WebSocket)
Агент умеет вызывать 3 функции (см. [`appendix/api-inventory.md`](./appendix/api-inventory.md#ai-инструменты-function-calling)), которые delegируют напрямую в `TripService` — то есть любое изменение через чат физически идёт по тем же бизнес-правилам, что и explicit REST-вызовы из UI. Агенту явно запрещено раскрывать пользователю сырые UUID точек.

### Известные незавершённые/«мёртвые» участки (важно для бэклога)
- Компоненты `OnboardingStep3` (выбор ритма поездки), `OnboardingStep4` (фейковый экран «генерации») и `ActiveTripPage` (полностью замоканный «live»-экран поездки) существуют в коде, но не подключены к роутингу — ритм поездки хардкодится как `"balanced"`.
- Поле для заметки «идеальный день» (шаг стиля) и заметка о попутчиках (шаг состава группы) собираются в UI, но никуда не отправляются.
- Множественный выбор карточек поездок на дашборде (чекбоксы) реализован в UI, но не имеет привязанного массового действия.
- Разфиналиация дня («Вернуть к редактированию») — чисто клиентское состояние (Set в памяти компонента), не сохраняется на бэкенде; после перезагрузки страницы отменить финализацию нельзя.
- В `.env` фронтенда переменная `VITE_API_URL`, судя по всему, содержит некорректно вставленное значение (запятая + markdown-ссылка вместо одного чистого URL) — требует проверки в конфигурации окружения.
- Ошибка «не указаны даты поездки» при генерации маршрута выбрасывается как обычный `ValueError`, попадает в generic-обработчик и возвращается пользователю как **500**, а не как понятная 4xx-ошибка.

### Общие паттерны взаимодействия
- Все деструктивные действия (удаление поездки, удаление POI, отмена финализации дня) сопровождаются модальным подтверждением.
- Списки/маршруты сортируются по `sequence_order`, дни — по `day_number`.
- Оптимистичные обновления UI применяются при удалении/замене POI (локальное состояние обновляется до/без повторного полного рефетча).
- Интерфейс полностью на русском языке без библиотеки i18n — тексты жёстко закодированы в JSX.
