# Логистика маршрута относительно отеля — план (отложено)

> **Статус: отложено, не в работе.** Документ зафиксирован 2026-08-19 по
> итогам обсуждения, чтобы не потерять решения и обоснование. Не начинать
> реализацию без отдельного решения вернуться к этой теме. Формат — по
> образцу `RAG-POI-PLAN.md`/`FRONTEND-PLAN.md`: факты → архитектура →
> итерации.

## Зачем это вообще

Сейчас генерация маршрута никак не учитывает, где пользователь живёт во
время поездки. Цель — чтобы: (а) если отель уже известен, план физически не
уводил пользователя далеко от него; (б) если отеля ещё нет, продукт мог
порекомендовать, где имеет смысл жить, исходя из уже построенного маршрута.
Оба сценария нужны — не выбираем один вместо другого (решение от
2026-08-18: «функционал нужен для обоих случаев»).

## Установленные факты

1. **В генерации сейчас нет географических данных вообще.** Промпт
   `generate_trip` получает по каждому месту только `id`, `name`,
   `description`, `rules` ([ai.py:201-205](backend/app/services/ai.py#L201))
   — координаты (`POI.lat`/`POI.lon`, [poi.py:82-95](backend/app/models/poi.py#L82))
   не передаются. Модель рассуждает о логистике вслепую, по одним названиям.
   Это не проблема, специфичная для отеля — то же самое отсутствие данных
   стоит за нескоординированностью мест внутри одного дня (пункт
   «логистика между точками» в `PRODUCT-FEATURES.md`). Обе проблемы чинятся
   одним и тем же фундаментом (см. ниже), не отдельно.
2. **"Рядом с первым/последним местом" неоднозначно для многодневной
   поездки.** Без географической кластеризации по дням первое место дня 1 и
   последнее место дня 5 могут быть в разных концах города — один отель не
   может быть одинаково "рядом" со всеми днями сразу, если сами дни не
   собраны географически связно. Решение от 2026-08-18: один отель на всю
   поездку (не разные базы по дням/районам) — упрощает задачу, но не
   отменяет необходимость сначала собрать дни геометрически осмысленно.
3. **Инструмент для радиус-фильтра уже есть.** `POIRepository.get_nearby(lat,
   lon, radius_meters)` через PostGIS `ST_DWithin` ([poi.py:43-63](backend/app/repositories/poi.py#L43))
   уже реализован и используется в функции "рядом со мной". Прямо
   переиспользуется для флоу с известным отелем — не нужно писать
   геозапрос заново.
4. **RAG-отбор (`RAG-POI-PLAN.md`) — обязательная предпосылка, не
   альтернатива.** Кластеризовать по дням имеет смысл уже отобранный по
   интересам пул POI (top-k из RAG), а не весь каталог города — иначе в
   один географический кластер могут попасть места, не относящиеся к
   интересам пользователя, просто потому что они рядом друг с другом.
5. **Функция поиска отелей уже спланирована отдельно.** `FRONTEND-PLAN.md`,
   Итерация 6 — карточка поиска/сравнения отелей с диплинком наружу (без
   транзакции внутри продукта). Этот план не создаёт новую функцию поиска
   отелей — он только меняет, какая точка передаётся в неё как центр
   поиска (сейчас там нет входной точки вообще, по умолчанию был бы «центр
   города»).

## Архитектура — три стадии вместо одного вызова LLM

Вместо одного промпта, который просит модель одновременно учитывать
интересы, географию и логистику, — три последовательные, разного рода
стадии:

1. **RAG-отбор** — сузить каталог города до мест, релевантных интересам
   (уже спланировано отдельно).
2. **Геокластеризация по дням** — детерминированный алгоритм (например
   k-means по `lat`/`lon`, число кластеров = число дней поездки), не LLM.
   Минимизация расстояний — задача для арифметики, не для языковой модели,
   читающей список названий текстом. Результат — каждый день уже
   географически связный набор кандидатов, до того как LLM их увидит.
3. **LLM работает внутри готовых кластеров** — выбирает главные/запасные
   места, тему дня, расставляет время. Модель занимается тем, в чём она
   действительно сильна (смысл, формулировки, приоритизация), не тем, в чём
   ненадёжна (геометрия).

## Флоу А — отель уже известен

Технически самый дешёвый из двух вариантов, за счёт переиспользования
готового кода:

- При создании поездки — опциональный шаг «уже забронировали отель?» с
  адресом → геокодирование (тот же поставщик карт, что уже используется) →
  координаты сохраняются на `Trip`.
- **Перед** стадией RAG-отбора — пул кандидатов предварительно
  отфильтровывается радиусом от отеля через уже существующий
  `POIRepository.get_nearby`. RAG-ранжирование и геокластеризация по дням
  работают уже внутри суженного, близкого к отелю пула.
- Эффект: план физически не может увести далеко от отеля, потому что
  дальние места отсеяны ещё до того, как их увидела модель — не «попросили
  предпочитать близкое», а действительно убрали дальнее из выбора.

## Флоу Б — отеля ещё нет

Проще Флоу А и не требует совместной оптимизации «отель ↔ маршрут»
одновременно — обходит конфликт «курица-яйцо» тем, что вычисляет отель
**из уже готового** плана, а не подгоняет план под отель:

1. План строится как в основном сценарии (RAG + геокластеризация по дням,
   без ограничения по отелю).
2. После генерации вычисляется точка — центроид или геометрическая медиана
   первых/последних мест каждого дня, с весом по числу дней. Это и есть
   «рекомендуемый район проживания», выведенный из уже согласованного по
   логистике плана.
3. Точка передаётся в функцию поиска отелей (`FRONTEND-PLAN.md`, Итерация
   6) вместо города по умолчанию.

Если пользователь потом бронирует что-то по рекомендации — план
**не обязательно перегенерировать**: он уже был рассчитан так, чтобы
рекомендованная точка была для него оптимальной.

## Изменения в модели данных

- `Trip`: новое опциональное поле координат проживания (по аналогии с
  `POI.geom` — `accommodation_geom` или отдельные `accommodation_lat`/
  `accommodation_lon`). Заполняется пользователем (Флоу А) либо
  вычисляется после генерации и хранится как рекомендация (Флоу Б) — оба
  случая используют одно и то же поле, разница только в том, кто его
  заполнил и когда.
- Если поездка изначально прошла Флоу Б, а затем пользователь подтвердил
  реальный отель — то же поле обновляется по факту брони, план не
  трогается автоматически.

## Итерации (не начаты, зафиксированы для возврата к теме)

1. **Геокластеризация по дням** — общий фундамент для обоих флоу и заодно
   для существующей задачи «логистика между точками дня»
   (`PRODUCT-FEATURES.md`). Не зависит от отеля — можно и стоит делать
   независимо, даже если тема отеля останется отложенной дольше.
2. **Флоу А: поле координат отеля + предфильтр через `get_nearby`.**
   Меньше нового кода, чем кажется — использует существующий метод
   репозитория без изменений в нём самом.
3. **Флоу Б: вычисление рекомендуемой точки после генерации + связка с
   поиском отелей.** Зависит от Итерации 1 (нечего усреднять без
   геокластеризованных дней) и от готовности `FRONTEND-PLAN.md`, Итерация 6.
4. **UI: шаг «уже забронировали отель?» в онбординге / карточка
   рекомендации района.** Фронтовая часть, отдельно не детализирована в
   этом документе — при возврате к теме дополнить по аналогии с
   `FRONTEND-PLAN.md`.

## Открытые вопросы (на момент возврата к теме)

- Алгоритм кластеризации — k-means или что-то проще (жадная кластеризация
  по ближайшему соседу)? Не решалось — требует прогона на реальном
  распределении POI (сейчас это всего 2 города, 174 и 172 места — решение
  стоит принимать на более представительных данных).
- Что считать «геометрической медианой» при малом числе дней (1-2 дня) —
  вырожденный случай, требует отдельной проверки, не блокирует общую
  архитектуру.
