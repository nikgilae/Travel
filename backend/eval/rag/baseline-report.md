# Baseline-отчёт: лексический (TF-IDF) retrieval по POI

Итерация 0 плана [RAG-POI-PLAN.md](../../../RAG-POI-PLAN.md). Прод-код не менялся.
Ниже — воспроизводимая нижняя граница для сравнения с multilingual-embedding
подходом Итераций 1-3.

## Метод

- Корпус: `scripts/export_poi_corpus.py` → `eval/rag/corpus/*.txt`, один файл
  на POI (`name + description + information`), 346 документов — весь каталог
  (Манама + Бодрум), без фильтра по городу.
- Инструмент: `retrieval_evaluator.py` (skill `rag-architect`), встроенный
  TF-IDF, без внешних зависимостей. **Токенизатор — `\b[a-zA-Z0-9]+\b`,
  кириллица не индексируется вообще.** Это значит: русский текст запроса даёт
  нулевые токены; совпадения возможны только по английским словам. Именно
  поэтому `queries.json` намеренно содержит английские категорийные слова
  (`museum`, `cafe`, `bar`, `park`...) рядом с русской формулировкой — не
  потому что это естественный запрос пользователя, а потому что это
  единственный способ вообще получить сигнал от корпуса, который состоит из
  капитализированных Google Place types на английском
  ([app/core/maps.py:54](../../app/core/maps.py#L54)).
- Ground truth для 4 категориальных тегов (`cultural`, `food`, `nature`,
  `night`) построен программно: строка `description` каждого POI разбита по
  запятой, типы сопоставлены с тегом по явной таблице (например
  `museum`/`church`/`art gallery`/`place of worship`/`mosque`/`hindu temple` →
  `cultural`). Это не LLM-разметка и не гипотеза — прямое соответствие
  реальным Google Place types, обнаруженным в корпусе.
- 12 запросов, по 2 на каждый из 6 тегов
  ([frontend/src/pages/OnboardingStyle.jsx:17-22](../../../frontend/src/pages/OnboardingStyle.jsx#L17)).

| Метрика | Значение |
|---|---|
| Precision@1 | 0.875 |
| Precision@5 | 0.875 |
| Precision@10 | 0.875 |
| Recall@1 | 0.018 |
| Recall@5 | 0.093 |
| Recall@10 | 0.187 |
| MRR | 0.938 |
| NDCG@5 | 0.870 |

Разбивка ground truth по тегам (сколько POI из 346 реально размечены под
тег): `food` — 91, `night` — 84, `cultural` — 32, `nature` — 25.

Полный вывод (per-query метрики, failure analysis) — `eval/rag/baseline-results.json`.

## relaxed / active — намеренно не измерены

`relaxed_1`, `relaxed_2`, `active_1`, `active_2` отсутствуют в
`ground_truth.json` как ключи — не пропущены по ошибке. Evaluator корректно
это обрабатывает: печатает `Warning: No ground truth found for query <id>` и
исключает эти запросы из агрегатных метрик (подтверждено в выводе прогона).
Причина — факт 4 плана: `relaxed`/`active` — темп/вайб, не категория места;
любая категориальная разметка для них была бы фальшивой, а не просто
неточной. Эти два тега не решаются retrieval-ом по текущим полям POI в
принципе, независимо от алгоритма (TF-IDF, embedding — не важно) — это
подтверждает раздел плана про Итерацию 4 (`activity_level` как альтернативное
решение, не через retrieval POI).

## Почему цифры отличаются от раздела "Установленные факты" в плане

В плане зафиксирован **другой** прогон: 174 POI только Манамы, ручная
разметка по тем же 4 тегам, без явного добавления английских категорийных
слов в первой итерации запросов ("первый прогон, до подстановки словаря
тегов", Precision@5=0.75, Recall@5=0.07, MRR=0.75). Этот отчёт — новый,
воспроизводимый прогон на полном корпусе (346 POI, 2 города) с
программной (не ручной) категориальной разметкой и запросами, сразу
включающими англоязычную категорийную лексику. Оба прогона показывают одно и
то же структурно:

- **Precision высокий, recall низкий — и это ожидаемо, не баг.** При 84
  релевантных POI в `night` top-5 физически не может покрыть больше 5/84.
  В проде используется top-`MAX_POIS_FOR_AI` (40-100), а не top-5 — там recall
  будет кардинально выше по построению (Итерация 3 должна измерить это
  отдельно на реалистичном k, не k=5).
- **Лексическое совпадение работает только при точном пересечении словаря
  запроса и корпуса.** Здесь это дало высокую точность именно потому, что
  английские категорийные слова подставлены в запрос вручную — то есть это
  не работоспособное решение для прода (пользователь не пишет "museum
  cafe bar" в свободном тексте), а верхняя граница для лексического подхода
  при идеальном словаре. В проде реальный запрос — это `interests` (6 тегов
  as-is) + свободный `notes` на русском, без ручной подстановки словаря.
  Это ровно тот разрыв, который должен закрыть multilingual embedding
  (Итерация 1-3): понимать `"хочу погулять по музеям"` без явного слова
  `museum` в запросе.

## Вывод

TF-IDF-baseline подтверждает нижнюю границу и структурные ограничения
recall@k при малом k — ожидаемо, не повод для тревоги. Ключевой вывод для
следующих итераций: лексический подход **работоспособен только при ручной
подстановке англоязычного словаря категорий**, что не является решением для
прода. Это усиливает (не меняет) аргумент плана в пользу multilingual
embedding-модели, а не keyword-matching. `relaxed`/`active` подтверждённо не
решаются на текущих данных POI никаким retrieval-подходом — откладываются до
Итерации 4 (проверка через обогащённый текст) с ожиданием, что и там сигнала
может не быть, и тогда решение — не retrieval, а `activity_level`.

Прод-код не изменён. Итерация 0 завершена.
